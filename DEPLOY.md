# Deploy AI Mystery with Render and MongoDB Atlas

This setup deploys the React build and Express API together as one Render web service. The browser talks to `/api/v1` on the same host, so session cookies stay first-party and no separate frontend CORS configuration is needed. Render's [Node/Express deployment guide](https://render.com/docs/deploy-node-express-app) covers its web service build and start commands.

## 1. Prepare the repository

1. Create a private or public GitHub repository and push this project to its default branch. Do not commit `.env` files or API keys; `.gitignore` excludes them.
2. Keep `render.yaml` in the repository root. Render reads it as a Blueprint and prompts for the two secret values.

## 2. Create the MongoDB Atlas database

1. Sign in to [MongoDB Atlas](https://cloud.mongodb.com/), create a project, and create a cluster. Pick a region close to the Render service region you plan to use.
2. In **Security → Database Access**, create an application database user with a strong password. Give it read/write access to the `ai_mystery` database; this is separate from your Atlas website login.
3. In **Database → Connect → Drivers**, choose Node.js and copy the connection string. Replace the password placeholder with the database user's password. URL encode special characters in the username or password.
4. Set the database name in the URI to `ai_mystery`, for example:

   ```text
   mongodb+srv://DB_USER:URL_ENCODED_PASSWORD@cluster.example.mongodb.net/ai_mystery?retryWrites=true&w=majority
   ```

5. Atlas only accepts connections from addresses on its project IP access list. After Render creates the service, copy its [outbound IP ranges](https://render.com/docs/outbound-ip-addresses) from **Render service → Connect → Outbound**, then add those CIDR ranges under **Atlas → Security → Network Access → IP Access List**. If you later change Render regions or outbound IP settings, update this list too. Avoid `0.0.0.0/0` for a deployed database; Atlas warns that it permits connections from anywhere in its [IP access list documentation](https://www.mongodb.com/docs/atlas/security/ip-access-list/).

## 3. Get a Gemini API key

Create an API key in [Google AI Studio](https://aistudio.google.com/app/apikey). Keep it private; it belongs only in Render's server environment and must never use a `VITE_` variable.

## 4. Create the Render service

1. In the [Render Dashboard](https://dashboard.render.com/), choose **New → Blueprint** and connect the GitHub repository.
2. Render finds `render.yaml`. Enter the Atlas URI for `MONGODB_URI` and the Google key for `GEMINI_API_KEY` when prompted. `SESSION_SECRET` is generated by Render.
3. Apply the Blueprint. The service uses these commands:

   ```text
   Build:  npm install && npm install --prefix client && npm install --prefix server && npm run build --prefix client
   Start:  npm start
   ```

4. In the service settings, choose the same region used for Atlas. Copy the service's outbound CIDR ranges as described above, allow them in Atlas, and redeploy if the first startup could not connect to MongoDB.
5. Confirm the Render Environment page contains `NODE_ENV=production`, `GEMINI_MODEL=gemini-3.8-flash`, `SESSION_SECRET`, `MONGODB_URI`, and `GEMINI_API_KEY`. Render supplies `PORT` automatically. Do not set `VITE_API_BASE_URL` to a localhost URL in production.

The built client is served by Express, and production API calls use the same-origin `/api/v1` path. Render's health check uses `/api/v1/health`.

## 5. Confirm the deployment

1. Open `https://YOUR-SERVICE.onrender.com/api/v1/health`. A healthy deployment responds with JSON showing both `application` and `database` as `available`.
2. Open the service root. The Casefile Studio landing page should load.
3. Choose **Create a case**, enter a premise of 50–2,000 characters, generate a case, inspect evidence, and submit an accusation.
4. Refresh the investigation and verdict pages. The same case, discovered evidence, and final result should remain.
5. If generation fails, check **Render → service → Logs** for the server-side error, then confirm the Gemini key, model setting, and provider quota. Never paste secrets into logs or support tickets.

## 6. Optional custom domain

Add a domain in **Render → service → Settings → Custom Domains**, then create the DNS records Render provides. The client and API remain on that same domain, so no frontend API URL or CORS change is needed.

## Local deployment rehearsal

Use Node.js 20 or newer. Install root, client, and server dependencies, copy `server/.env.example` to `server/.env`, fill in the Atlas URI, Gemini key, and a random `SESSION_SECRET` of at least 32 characters, then run `npm run dev:full`. The local client proxies `/api` to Express. `npm run dev` alone intentionally starts the no-credentials sample demo.

## Hosting note

The included Blueprint selects Render's Free web-service plan for an inexpensive first deployment. Render currently spins free web services down after 15 minutes without traffic, and a waking service can take about a minute to respond. Render says its free instances are intended for previews and hobby use, not production. For a public launch where predictable response time and uptime matter, change the service to a paid plan in Render. [Render free-service limits](https://render.com/docs/free)
